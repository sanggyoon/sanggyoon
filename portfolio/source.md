[portfolio - 카카오 AIaaS]

- 프로젝트 개요
  - 4인 팀 팀장으로 참여
  - 기획 제외 인프라·프론트·백엔드·DB·ML·DevOps 전 영역 주도

- 하이브리드 클라우드
  - 제공받은 KakaoCloud를 메인 환경으로 사용
  - VM 5대 기반 셀프매니지드 Kubernetes로 서비스 운영 (k3s)
  - 정해진 인스턴스만 사용하지 않고 AWS를 DR 환경으로 사용하여 안정적인 서비스 구축

- DR 비용 최적화
  - DR 환경에서 관리형 NAT Gateway·EIP 제거
  - 앱·DB를 퍼블릭 서브넷과 공인 IP로 전환
  - Security Group으로 인바운드 최소화
  - DB 인스턴스를 t3.medium에서 t3.small로 다운사이징
  - 상시 운영비를 월 약 $110에서 $49로 절감

- DR 자동화
  - Terraform으로 AWS DR 인프라 코드화
  - 네임서버를 가비아에서 AWS Route53으로 변경하고 헬스체크 기반 자동 페일오버 구현 및 테스트

- CI/CD 자동화
  - GitHub Actions → GHCR → Argo CD GitOps 파이프라인 구축
  - Git을 단일 진실 소스로 활용하여 선언적 배포·롤백 구성

- 부하 테스트 및 최적화
  - 서비스 클러스터와 분리된 별도 VPC·VM에 k6를 구성해 실서비스 영향 없이 부하 인가, 점진 램프업 + p95 3초/에러율 5% 초과 시 자동 중단으로 안전하게 진행
  - 응답 지연을 경로별(FE 페이지·DB 조회·BE 처리)로 분리 계측하고 Grafana·Loki로 HPA 확장·노드 CPU를 실시간 관찰
  - 1차: 500 VU에서 p95 2.12s·에러율 0%로 안정. HPA 정상 동작 확인(FE 2→6, BE 1→4 자동확장·복귀)
  - 병목 규명: 붕괴점을 직접 탐색해 ~713 VU에서 단일 DB 노드 CPU 100% 포화가 천장임을 입증 — 자동확장되는 앱 티어가 아니라 단일 노드가 한계임을 데이터로 확정
  - 캐시 개선(라우트 캐싱 1h + 페이로드 축소): DB 천장 제거로 한계 ~700 → 2000+ VU(3배↑), p95 4.5s → 0.66s, DB CPU 100% → 20%
  - 한계 재이동: FE HPA max 8→16 상향 후 붕괴점 ~3600 VU로 확장(초기 대비 약 5배), 천장이 app 워커 노드로 이동함을 확인 → 후속 개선안으로 노드 증설 도출
  - 외부 스코어 API: 인증 결과 캐싱(60s) + PostgREST 커넥션 풀 10→40 튜닝으로 인증·데이터 노드 천장 제거, 한계 ~500 → ~3777 VU(약 7배↑)
  - 측정 방법론 정립: 부하 도구가 캐시를 우회하면 개선 효과가 측정되지 않는 점, 부하 생성기 자체 한계(ulimit)를 서비스 천장으로 오인하면 안 되는 점을 진단 과정에서 규명

[portfolio - 종합설계 TeamTalk]

- 프로젝트 개요
  - 4인 팀 팀장, 인프라·백엔드 중심 풀스택 담당
  - 멀티 AI 에이전트 상호작용 서비스(ABORA)를 v1 설계 후 v2로 재설계·고도화

- 아키텍처 설계
  - 역할별 소형 모델(Qwen, Llama, Mistral, 7~8B) + 오케스트레이터 구조를 n8n으로 구성
  - 사용자 입력에 대해 어떤 역할 모델이 언제 응답할지 라우팅·조율하는 협업 파이프라인 설계
  - 모노로식 구조의 프로토타입(v1)에서 프론트/백엔드 분리 구조로 재정비(v2), 데이터 흐름을 프론트→백엔드→DB 저장까지 일관되게 연결

- 추론 인프라 구축
  - Mac mini 홈서버(M4·16GB)에 Ollama·n8n·Nginx로 온프레미스 추론 환경 구성
  - 로컬 LLM 상주 서빙 + 리버스 프록시 기반 요청 처리

- 성능 최적화 (언어 모델 응답시간 5분 → 3분, 약 40% 단축)
  초기 응답이 5분 이상 걸린 원인은 두 가지였습니다.
  - 메모리 초과: 역할별 소형 모델을 여러 개 동시에 메모리에 상주시키자 16GB가 부족해졌고, 부족분을 SSD로 스와핑하면서 전체 속도가 급격히 느려짐.
  - 자원 충돌: 여러 모델이 동시에 추론을 돌리며 단일 노드의 CPU·메모리를 서로 경쟁, 동시 처리가 오히려 지연을 유발.
    이에 두 가지 기법으로 대응했습니다.
  - 지연 로드(lazy load) : 모든 모델을 상주시키지 않고, 해당 모델의 차례가 왔을 때만 메모리에 올려 상주 모델을 최소화. 메모리 초과로 인한 스와핑을 제거 (트레이드 오프: 첫 호출 시 로딩 지연은 감수).
  - 요청 직렬 큐 : 동시 추론을 막고 요청을 순서대로 하나씩 처리. 각 추론이 자원을 온전히 점유해 개별 응답이 빨라지고 처리 시간이 예측 가능해짐
    두 기법을 결합해 응답 시간을 약 3분까지 단축했습니다.

- 리소스 제약 대응
  - 16GB 단일 노드 한계를 고려해, 전체 파인튜닝 대신 Nvidia 그래픽 카드를 사용하여 LoRA 기반 역할 분리 학습으로 범위 조정

- 성과
  - 최우수상 수상
  - 설계·아키텍처·결과 정리 기여분이 논문 1편에 반영, 공저자 등재

[portfolio - 지존소프트 인턴]

- 프로젝트 개요
  - 개발부 인턴으로 참여

- 인프라 구축
  - NAS(Synology DSM)에 메일 서버(SMTP)·Supabase·웹 서비스 배포 등 인프라 신규 구축

- 장애 대응
  - 상황
    - 베타 서비스 운영 중 웹 요청이 모두 504로 차단됨
    - 백엔드 서버 이전 직후 문제 발생 (하드웨어 물리적 위치 변경)
  - 분석
    - 레이어별로 문제를 각 엔드포인트부터 추적 (클라이언트 -> 서버, 서버 -> 클라이언트)
    - Nginx가 시작 시 해석한 이전 서버 IP를 계속 참조하는 DNS 캐싱이 원인임을 확인
  - 조치
    - 컨테이너 재시작으로 즉시 복구
    - Nginx resolver와 변수 기반 proxy_pass를 적용해 10초마다 도메인을 재해석하도록 변경
  - 결과
    - 서버 IP 변경 시 사람 개입 없이 자동 반영
    - 이후 동일 원인 장애 0건
    - 문서화하여 사내 커뮤니티에 저장
